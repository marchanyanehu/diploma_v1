**Минимальные требования к реализации серверной части для получения проходного балла**

Для успешной защиты дипломной работы серверная часть вашего приложения должна соответствовать следующим минимальным требованиям:

**1\. Использование современного фреймворка**

Приложение должно быть разработано с использованием высокоуровневого фреймворка, предназначенного для серверной разработки. Например, ASP.NET Core, Spring, Django, Node.js и другие.

**1.1 Исключение:** Если ваша работа предполагает разработку консольного приложения или другого типа программного обеспечения, логически не требующего использования фреймворков, вы обязаны самостоятельно реализовать функциональность, предоставляемую такими инструментами. Это включает:

\- Логирование;

\- Обработку ошибок;

\- Сериализацию и привязку данных (data binding);

\- Авторизацию и аутентификацию.

**2\. Работа с состоянием данных**

Если приложение хранит состояние объектов или данных, необходимо использовать базу данных. Выбор между реляционной (например, PostgreSQL, MySQL) и нереляционной (например, MongoDB) базой данных зависит от требований вашего проекта.

**3\. Использование ORM**

Взаимодействие с базой данных должно быть реализовано с использованием ORM (Object-Relational Mapping). Например, Entity Framework, Hibernate, Sequelize и другие.

**4\. Архитектура приложения**

Приложение должно следовать принципам многослойной архитектуры (например, разделение на уровни: представление, бизнес-логика, доступ к данным). Это обеспечит модульность и удобство поддержки кода.

**5\. Принципы проектирования (SOLID)**

Код приложения должен быть написан в соответствии с принципами SOLID:

\- Single Responsibility Principle (Принцип единственной ответственности);

\- Open/Closed Principle (Принцип открытости/закрытости);

\- Liskov Substitution Principle (Принцип подстановки Барбары Лисков);

\- Interface Segregation Principle (Принцип разделения интерфейсов);

\- Dependency Inversion Principle (Принцип инверсии зависимостей).

**6\. Описание интерфейса взаимодействия**

Интерфейс взаимодействия с серверной частью (API) должен быть четко описан. Это может быть сделано с использованием документации (например, OpenAPI/Swagger) или текстового описания, если проект не предполагает стандартных инструментов.

**7\. Глобальная обработка ошибок**

В приложении должен быть реализован централизованный механизм обработки ошибок. Это повысит его надежность и упростит отладку.

**8\. Логирование**

Приложение должно вести логирование ключевых событий, ошибок и других значимых операций. Логи должны быть структурированы и доступны для анализа.

**9\. Развертывание в рабочей среде**

Готовое приложение должно быть развернуто в продакшн-среде. Это может быть:

\- Облачное решение (например, AWS, Azure, Google Cloud, Heroku);

\- Приватные серверные ресурсы (например, Docker-контейнеры на локальном сервере).

Важно: вы должны продемонстрировать, что приложение работает и доступно для внешних пользователей.

**10\. Покрытие тестами**

Бизнес-логика приложения должна быть покрыта модульными тестами (unit tests). Минимальное требование к покрытию кода тестами - \*\*70%\*\*. Используйте инструменты для анализа покрытия кода, чтобы подтвердить этот показатель.

**Специфичные ограничения, технологии и подходы**

При разработке дипломной работы необходимо соблюдать следующие ограничения и рекомендации, чтобы обеспечить качество, безопасность и доступность вашего приложения:

**Общие ограничения**

- **Запрет на использование платных библиотек**  
    Не используйте платные библиотеки или инструменты, которые могут ограничить возможность проверки и использования вашего приложения другими пользователями. Ваше решение должно быть доступным и воспроизводимым.
- **Избегание уязвимых пакетов**  
    Проверьте используемые библиотеки и зависимости на наличие известных критических уязвимостей. Используйте инструменты анализа безопасности, такие как **npm audit**, **pip-audit**, или аналогичные для вашего стека технологий.
- **Работа в системе контроля версий**  
    Вся разработка должна проводиться в среде, поддерживающей контроль версий, например, Git. Репозиторий должен содержать историю изменений, чтобы можно было проследить ваш прогресс и подход к решению задач.
- **Использование JSON**  
    JSON должен быть основным форматом данных, используемым для передачи и обработки информации. Это обеспечит совместимость и удобство работы с большинством современных технологий.
- **Хранение секретов и конфиденциальных данных**  
    Все секретные данные (например, ключи API, пароли, токены) не должны храниться в репозитории. Они должны быть вынесены в защищенные хранилища или переменные окружения. Убедитесь, что ваш процесс развертывания учитывает этот аспект.
- **Автоматическое развертывание из репозитория**  
    Приложение должно быть способно разворачиваться и запускаться из последней версии в репозитории без необходимости ручных изменений или дополнительных "костылей". Это демонстрирует зрелость вашего подхода к разработке.

**Чего не следует делать**

- **Изобретение собственных протоколов шифрования**  
    Не создавайте собственные протоколы шифрования или кастомные реализации стандартных решений, таких как JWT. Используйте проверенные, стандартизированные технологии.
- **Использование устаревших или учебных библиотек**  
    Не используйте библиотеки, которые устарели или предназначены исключительно для учебных целей. Например:
  - **xmlrpc**;
  - Встроенный **http.server** в Python без доработок;
  - Другие инструменты, не предназначенные для продакшен-использования.
- **Создание заглушек вместо API**  
    Приложение не должно возвращать статический JSON или другие фиктивные данные вместо полноценного взаимодействия с базой данных или другими компонентами. Это считается недопустимым упрощением.

**Рекомендации по модульности**

- Приложение должно быть модульным. Код должен быть структурирован в соответствии с принципами модульности, чтобы избежать монолитного подхода (например, весь код в одном файле). Это упрощает поддержку, тестирование и масштабирование приложения.

**Максимальные требования к реализации серверной части дипломного проекта**

Для получения высшей оценки (10 баллов) серверная часть вашего дипломного проекта должна демонстрировать продвинутые практики разработки, развертывания и поддержки приложений. Выполнение следующих требований позволит вам показать глубокие знания и навыки:

**1\. Внедрение CI/CD практики**

- Автоматизация сборки, тестирования, упаковки и развертывания приложения с использованием CI/CD (Continuous Integration/Continuous Deployment).
- Примерный процесс:
  - Создание Docker-образа с вашим приложением;
  - Хранение образа в контейнерном регистре (например, Docker Hub, AWS ECR, GitHub Container Registry);
  - Автоматическое развертывание образа в продакшен-среде (например, в облаке: AWS, Azure, GCP или на локальном сервере).
- На этапе развертывания должны быть внедрены секреты (ключи, пароли, токены) и настройки через систему переменных окружения или секретных хранилищ. Все этапы должны быть выполнены через pipeline системы сборки и развертывания (например, GitHub Actions, GitLab CI/CD, Jenkins).

**2\. Микросервисная архитектура**

- Приложение должно состоять из нескольких микросервисов, каждый из которых выполняет свою четко определенную задачу.
- Микросервисы должны быть независимыми и иметь возможность развертывания в продакшен-среде отдельно друг от друга.

**3\. Асинхронное взаимодействие**

- Части приложения (микросервисы) должны взаимодействовать между собой асинхронно (например, через очереди сообщений - RabbitMQ, Kafka). Это обеспечит масштабируемость и устойчивость системы.

**4\. Кэширование**

- Реализация кэширования для оптимизации производительности. Например, использование Redis или Memcached для хранения временных данных, часто используемых запросов или результатов вычислений.

**5\. Мониторинг системы**

- Внедрение системы мониторинга состояния приложения и инфраструктуры.
- Использование инструментов, таких как Grafana и Prometheus, для:
  - Сбора метрик (нагрузка на процессор, количество запросов, использование памяти и т.д.);
  - Визуализации данных через дашборды.

**6\. Система работы с логами**

- Логи приложения должны быть структурированными и централизованными.
- Возможность фильтрации, поиска и анализа логов через специализированные инструменты, такие как ELK Stack (Elasticsearch, Logstash, Kibana) или Loki.
- Логи должны быть полезны для отладки и анализа работы системы.

**7\. Отслеживание запросов между микросервисами**

- Реализация механизма отслеживания цепочки запросов между микросервисами с использованием **correlation ID**. Это позволит отследить полный путь обработки запроса, даже если он проходит через несколько сервисов.

**8\. Система уведомлений (Alerting)**

- Настройка системы оповещений при возникновении определенных условий (например, превышение пороговых значений метрик, возникновение ошибок).
- Использование инструментов, таких как Alertmanager, для отправки уведомлений в мессенджеры (Telegram, Slack) или по электронной почте.

**9\. Quality Gates в CI/CD**

- Настройка "quality gates" в CI/CD pipeline. Это включает:
  - Автоматическую проверку качества кода (например, использование SonarQube или аналогов);
  - Запуск тестов (unit-тесты, интеграционные тесты);
  - Проверку покрытия кода тестами (например, минимальное покрытие - 80%).
- Развертывание должно происходить только при успешном прохождении всех проверок.

**Основные ошибки и недочеты, влияющие на оценку серверной части диплома**

Ниже приведен список ошибок и небрежностей, которые считаются недопустимыми и за которые будут вычитаться баллы из общей оценки дипломной работы. Эти моменты демонстрируют несоответствие современным стандартам разработки и снижают качество проекта.

**Ошибки в безопасности**

- **Использование небезопасных алгоритмов хеширования**  
    Пример: использование MD5 или SHA-1 вместо современных алгоритмов, таких как bcrypt, Argon2 или SHA-256.  
    **Минус 1 балл.**
- **Прямое хранение конфиденциальных данных**  
    Пример: хранение паролей или токенов в открытом виде вместо их шифрования или хеширования.  
    **Минус 1 балл.**
- **Отсутствие валидации входных данных**  
    Пример: отсутствие проверки пользовательского ввода, что может привести к SQL-инъекциям, XSS и другим атакам.  
    **Минус 1 балл.**

**Ошибки в обработке данных и ошибок**

- **Отсутствие обработки ошибок**  
    Пример: приложение падает при возникновении исключений, вместо того чтобы корректно обрабатывать их и возвращать понятные сообщения пользователю или системе.  
    **Минус 1 балл.**
- **Неверное использование HTTP-кодов или их отсутствие**  
    Пример: приложение всегда возвращает **200 OK**, даже при ошибках (например, при отсутствии ресурса).  
    **Минус 1 балл.**
- **Несогласованность с базой данных**  
    Пример: API не работает с заявленными сущностями, поля в базе данных не соответствуют описанию в документации.  
    **Минус 1 балл.**

**Ошибки в проектировании и коде**

- **Отсутствие API-документации**  
    Пример: отсутствие описания методов API, их параметров и возвращаемых данных (например, через Swagger или текстовую документацию).  
    **Минус 1 балл.**
- **Плохое качество кода**  
    Пример: нечитаемый, плохо структурированный код, отсутствие комментариев, использование неочевидных конструкций.  
    **Минус 1 балл.**
- **Неэффективные запросы к базе данных**  
    Пример: использование "жадных" запросов, отсутствие индексов, избыточное количество запросов вместо оптимизированных операций.  
    **Минус 1 балл.**
- **Хардкод конфигураций**  
    Пример: параметры, такие как URL базы данных, ключи API, пути к файлам, указаны прямо в коде вместо использования переменных окружения.  
    **Минус 1 балл.**
- **Отсутствие модульности**  
    Пример: весь код написан в одном файле, отсутствует разделение на слои (например, контроллеры, бизнес-логика, доступ к данным).  
    **Минус 1 балл.**
- **Использование "магических строк"**  
    Пример: строки или числа, используемые в коде без объяснения их значения (например, **"admin"** вместо константы **ROLE_ADMIN**).  
    **Минус 1 балл.**
- **Дублирование кода**  
    Пример: повторяющиеся блоки кода вместо вынесения их в функции или методы.  
    **Минус 1 балл.**

**Ошибки в тестировании**

- **Отсутствие покрытия тестами**  
    Пример: отсутствие unit-тестов или их недостаточное количество (менее 70% покрытия).  
    **Минус 1 балл.**

**Ошибки в реализации API**

- **Несоответствие REST-подходу**  
    Пример: неправильное использование методов HTTP (например, использование **GET** для создания ресурса), отсутствие логической структуры URL.  
    **Минус 1 балл.**
