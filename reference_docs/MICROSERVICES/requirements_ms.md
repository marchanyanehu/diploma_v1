**🎯 Микросервисная архитектура**

**Замечания и контекст**

Микросервисная архитектура подходит для проектов, где есть четкое разделение бизнес-доменов и необходимость в независимом масштабировании компонентов. Не стоит использовать микросервисы просто ради микросервисов - архитектура должна решать конкретные проблемы проекта.

**Важно:** Минимум 3 сервиса для демонстрации распределенной системы. Простое разделение frontend/backend/db НЕ считается микросервисной архитектурой.

**📋 МИНИМАЛЬНЫЕ ТРЕБОВАНИЯ (на 5 баллов)**

**1\. Документация**

**Обязательные разделы:**

- **Архитектурная диаграмма:** все сервисы, их взаимодействие, протоколы
- **Domain model:** границы контекстов (bounded contexts)
- **API документация:** контракты между сервисами (OpenAPI/AsyncAPI)
- **Deployment диаграмма:** как сервисы развертываются
- **Обоснование декомпозиции:** почему именно такое разделение

**2\. Архитектура**

**Разделение на сервисы:**

- Минимум 3 бизнес-сервиса (не считая инфраструктурные)
- Каждый сервис отвечает за отдельный бизнес-домен
- Сервисы могут работать независимо (loose coupling)
- Отсутствие shared database (у каждого своя БД или схема) - или обоснование почему необходимо

**Коммуникация:**

- Синхронная: REST API или gRPC между сервисами
- Четкие контракты взаимодействия (версионированные API)
- Таймауты и retry политики для всех вызовов
- Обработка недоступности зависимых сервисов

**3\. Реализация**

**Каждый сервис должен:**

- Иметь собственную кодовую базу (можно в монорепозитории)
- Собираться в отдельный Docker образ (если выбран критерий контейнеризация)
- Иметь независимую БД или изолированную схему
- Предоставлять health/ready endpoints
- Логировать с correlation ID для трассировки

**API Gateway или точка входа:**

- Единая точка входа для внешних клиентов
- Маршрутизация запросов к сервисам
- Базовая аутентификация/авторизация

**4\. Обработка ошибок**

- Graceful degradation при недоступности сервиса
- Возврат частичных результатов где возможно
- Правильные HTTP коды ошибок
- Централизованное логирование ошибок

**5\. Тестирование**

- Unit-тесты для каждого сервиса
- Интеграционные тесты критических flows
- Contract testing между сервисами

**6\. Ограничения**

**Что НЕЛЬЗЯ делать:**

- ❌ Синхронные вызовы по цепочке >3 сервисов
- ❌ Прямой доступ к БД другого сервиса
- ❌ Общие библиотеки с бизнес-логикой
- ❌ Distributed transactions (2PC)
- ❌ Монолит, разделенный только на папки

**🚀 МАКСИМАЛЬНЫЕ ТРЕБОВАНИЯ (на 10 баллов)**

_Все минимальные требования ПЛЮС минимум_ **_2-3 направления_**_:_

**📬 Направление 1: Асинхронная коммуникация**

**Если выбрано это направление:**

- Message broker (RabbitMQ, Kafka, NATS)
- Event-driven архитектура с событиями домена
- Pub/Sub паттерн для loose coupling
- Dead letter queues для failed messages
- Идемпотентность обработчиков
- Event sourcing (опционально)

**🔄 Направление 2: Resilience patterns**

**Если выбрано это направление:**

- Circuit breakers (Hystrix pattern)
- Bulkheads для изоляции ресурсов
- Rate limiting между сервисами
- Retry with exponential backoff
- Timeout management
- Fallback механизмы

**🔍 Направление 4: Observability**

**Если выбрано это направление:**

- Distributed tracing (Jaeger/Zipkin)
- Correlation IDs через все сервисы
- Centralized logging (ELK/Loki)
- Metrics collection (Prometheus)
- Custom business metrics
- Service dependency mapping

**🎪 Направление 5: Advanced patterns**

**Если выбрано это направление:**

- Saga pattern для распределенных транзакций
- CQRS для разделения чтения/записи
- API composition pattern
- Backend for Frontend (BFF)
- Service registry и discovery
- Database per service с синхронизацией

**🚪 Направление 6: API Management**

**Если выбрано это направление:**

- Advanced API Gateway (Kong, Zuul)
- Rate limiting per client
- API versioning strategy
- Request/Response transformation
- Caching на уровне gateway
- OAuth2/JWT authentication

**💡 Рекомендации**

**Когда НЕ нужны микросервисы:**

- Простое CRUD приложение
- Нет четких границ доменов

**Хорошие примеры декомпозиции:**

- 🛒 **E-commerce:** Orders, Inventory, Payments, Users, Notifications
- 🎬 **Streaming:** Content, Users, Recommendations, Analytics, Billing
- 🚖 **Ride-sharing:** Rides, Drivers, Passengers, Payments, Tracking
- 🍔 **Food delivery:** Restaurants, Orders, Delivery, Payments, Reviews

**Анти-паттерны для избежания:**

- ❌ Entity services (UserService, ProductService)
- ❌ Слишком мелкие сервисы (CRUD для одной таблицы)
- ❌ Слишком крупные сервисы (мини-монолиты)
- ❌ Циклические зависимости между сервисами
