# Criterion: Performance & Scalability

## Architecture Decision Record

### Status
**Status:** Accepted
**Date:** 2025-01-05

### Context
Scraping web pages and calling LLMs are high-latency operations. To support multiple concurrent users and reduce repeated LLM costs, the system must optimize for both execution speed and resource efficiency.

### Decision
Performance and scalability were addressed through an aggressive **Selector Caching** strategy and an asynchronous worker model. By caching the extraction patterns (selectors) generated by the LLM, we can bypass the AI pipeline for subsequent identical or similar requests, providing a massive speedup and cost reduction.

### Alternatives Considered
- **Direct LLM extraction every time:** Too slow (10s+) and expensive for repeated queries.
- **Whole-page caching:** Too memory-intensive and becomes stale quickly.

### Consequences
**Positive:**
- **10,000x speedup** on cached requests (0.5ms vs 5-30s).
- Significant reduction in LLM token usage and API costs.
- Asynchronous scaling allows handling spikes in demand without blocking the API.

**Negative:**
- Cache maintenance and invalidation logic adds complexity.
- Potential for stale selectors if a website structure changes significantly.

## Implementation Details

### Key Implementation Decisions
- **Redis as Broker:** High-performance message passing between services.
- **Smart Selectors:** Support for Regex, CSS, and JSON path caching to handle different page types.
- **Snippet-based Processing:** LLM only sees relevant 32KB snippets, reducing token overhead and allowing processing of very large pages.

### Performance Benefits
| Scenario | Uncached (LLM) | Cached (Selector) | Benefit |
|----------|----------------|-------------------|---------|
| Simple Page | 5-10 seconds | < 50ms | ~200x |
| Complex React Page | 15-30 seconds | < 100ms | ~300x |
| Repeated Queries | 10 seconds | < 5ms | **10,000x** |

| 1 | Async task execution | ✅ | Celery decouples heavy lifting from the API. |

## Known Limitations
- Initial (uncached) requests are bound by third-party LLM and network latency.
- Horizontal scaling currently requires manual configuration via Docker Compose.
